# 아카이브: 공유 라이브러리 보고서의 실측 절(§6–§9, 2026-09-17~18) — 공유 코어·C6 켜진 세팅

(`docs/shared_library_prefetch_report.md`에서 분리. 세팅의 문제는 `docs/archive/campaign_20260917_shared_regime.md` 머리말 참조.)

## 6. 실측 (2026-09-17 밤, DeathStarBench user-timeline, 자세한 표는 `flat_codegen/dsb_build/postlink/RESULTS.md`)

§3의 우회 방법을 전부 구현해서 재빌드 없이 stock 바이너리와 .so에 적용했다.

- **call 사이트 stub, PLT 엔트리 재작성, 요청당 hot-set burst**: 모두 효과 0(프리페치를 NOP으로 바꾼 쌍둥이와 같음).
- **trace 기반 배치**(어느 call 사이트에서 몇 사이클 뒤 어느 라인이 miss 나는지 LBR로 찾아 그 사이트에 넣음, 다른 .so의 라인은 GOT를 기준으로 주소 계산): miss 11% 감소(MPKI 22.3→19.8), 그러나 stub 때문에 명령이 5.7% 늘어 실제 CPU 시간은 **1% 개선**에 그침.
- **전면 재빌드**(서비스와 thrift·mongoc·bson·jaeger를 clang-19 + 우리 IR pass로 다시 컴파일, callee-burst 또는 seq 모드): 효과 0(1.001x / 0.992x). 라이브러리 안에 프리페치를 넣을 수 있게 되어도 miss가 줄지 않는다.
- **trace 기반 배치를 재빌드로 inline 주입**(stub 없음, 공유 라이브러리도 GOT 기준으로 같이 주입): 비고정 1.012x, 메인 스레드 전용 코어 + 워커 풀 4코어 고정 시 1.003x(miss 5.7→5.5). 삽입 비용을 없애도 남는 이득은 1% 안팎이다.
- **cold start 손실의 분해(공유 vs 격리, 명령 1,000개당)**: L2 코드 miss 15.2→2.6, 분기 예측 실패 7.6→2.7, L2 데이터 miss 5.2→2.5, ITLB/DTLB 워크 0.9/0.7→0.2/0.2, CPI +0.44. 코드 miss가 가장 큰 단일 성분(약 절반), 분기 예측 실패 20~25%, 데이터 miss 25~30%, TLB는 10% 미만. 즉 "코드 miss는 손실의 1/4"이라는 앞의 추정은 틀렸다: miss는 중요하지만, 소프트웨어 프리페치가 그것을 회수하지 못한 이유는 fill이 분기 많은 front-end의 수요보다 늦게 도착해서이고(제거한 miss 1%당 0.16%), 분기 예측기·데이터 몫은 프리페치 대상이 아니다.
- **왜 헛도는가(카운터로 확인)**: plan이 넣은 프리페치 4.3억 개/30초 중 실제로 라인을 가져온 건 0.2~1%뿐이다. miss는 요청이 도착한 직후 네트워크 읽기·역직렬화 코드(libthrift·libstdc++·libc)에서 한꺼번에 나는 "cold start"이고, 우리 코드의 프리페치 지점이 실행될 때는 이미 다 데워져 있다. 요청이 오기 전에는 무엇을 당길지 알아도 당길 시점이 없다.
- **wake-up 직후 데우기(커널 switch-in warm-up의 유저 공간 실험)**: 요청 하나가 5.6번 잠들었다 깨고 그때마다 ~2,400라인이 miss 난다. recv/poll이 리턴하는 순간(= 커널이 스레드를 다시 올린 직후)에 "wake 이후 사용 순서"로 정렬한 라인을 당기면 프리페치의 43%가 실제로 라인을 가져온다(코드 안 plan은 1%). 그러나 한 번에 64~128라인까지만 유효하고(fill queue 32~48개 한계, 그 이상은 버려짐) 결과는 **1.019x**. 32라인씩 쉬어가며 1,024라인을 넣으면 miss는 16% 줄지만 쉬는 시간이 miss 시간과 맞먹어 **0.982x**. 커널에서 같은 방식으로 해도 같은 벽에 부딪힌다.
- **wake 이후 miss의 시점**: 2 µs 안 1.4%, 5 µs 안 5.8%, 10 µs 안 13%, 절반은 40 µs 이후(실행 구간 중앙값 65 µs). 즉 커널이 switch-in 리드(0.5~1.5 µs)로 미리 채울 수 있는 몫은 miss의 1~2%다. 84%가 taken 분기 목적지에서 나므로 하드웨어 next-line 프리페처가 이어받을 순차 부분은 이미 잡히고 있고, 남는 건 65 µs에 흩어진 분기 목적지들이다.
- **완전 격리(다른 컨테이너를 서비스 코어에서 치움)**: miss 1.9 MPKI, CPU 시간 비고정 대비 39% 감소(1.64x). 그 위에서 wake-up 웜업을 다시 재면 **1.002x**(쌍둥이 1.001x): 격리된 코어는 요청 사이에 idle이라 L2가 그대로 남고, 데울 것이 없다. 커널 switch-in 웜업의 이점(커널의 전환 작업 1~3 µs와 겹치기, 오염 여부를 알고 건너뛰기, futex/타이머 wake까지 포착)은 공유 코어에서만 몇 % 가치가 있고 격리 코어에서는 0이다.
- **대조군: 서비스를 코어 4개에 고정**: miss가 22.5→6.4로 1/3.5, CPU 시간 **33% 감소**. 즉 이 서비스의 명령어 miss는 코드가 커서가 아니라(hot 라인은 66 KB뿐) 86개 코어를 26개 컨테이너가 나눠 쓰며, 스레드가 요청 사이 쉬는 30 ms 동안 다른 컨테이너가 그 코어의 L2를 지우기 때문이다.

시사점: 공유 라이브러리 문제는 §3·§4의 방법으로 기술적으로는 풀 수 있지만(cross-DSO 주소도 GOT anchor로 해결됨), 데이터센터 서비스의 miss 원인이 "예측 가능한 스트림"이 아니면 프리페치 자체가 답이 아니다. §4-2의 호출 대상 힌트도 이 경우 lead가 부족해 같은 한계를 가진다. 반면 flattened 시뮬레이터처럼 한 파일 안의 순차 스트림은 현재 ISA로도 충분히 잡힌다.

## 7. cold start 워크로드 스크리닝 (2026-09-17 오후, 기본 Linux 스케줄러 + co-tenant 부하)

컨테이너 25개를 코어 36개에 섞어 돌리고 하나씩 전용 코어로 빼서 miss 차이를 재는 방식으로 넓게 스크린했다(`RESULTS.md`).
- **cold start가 지배적인 워크로드는 흔하다**: PostgreSQL(공유 6.0 → 격리 0.1 MPKI, CPU 1.88x), compose-post(22.9 → 4.4, 1.77x), user-timeline(21.9 → 1.9, 1.64x), MariaDB durable(12.0 → 3.8, 1.33x). RPC 서비스와 DB가 모두 해당된다.
- **소프트웨어 프리페치로 잡히는 몫은 작다**: user-timeline에서 wake 직후 burst(1.019x), inline plan(1.005x), 정확한 call 사이트에 둔 post-link timeline plan(0.995x), MariaDB wake burst(트랜잭션당 사이클 동일), PostgreSQL wake burst(tps 1.012x, 쌍둥이 1.004x, miss 불변). 원인은 §6과 같다: miss가 wake 후 65 µs에 흩어진 분기 목적지들이고, 한 번에 발행할 수 있는 프리페치는 32~48개다.
- 한 예외는 **home-timeline**: 격리해도 5.3 MPKI였는데 코어의 C6 idle 상태를 끄면 0.1 MPKI, CPU 23% 감소. 코어가 요청 사이에 C6로 들어가며 L2를 비우는 경우로, 해법은 프리페치가 아니라 idle 정책이다.

결론은 §4-4와 같다. 이 부류의 손실은 실재하고 크지만(1.3~1.9x), 명령 프리페치 *명령*으로는 잡히지 않고, 스케줄링·idle 정책 또는 실행과 병렬로 스트리밍하는 하드웨어 warm-up 엔진의 영역이다.

## 8. "GOT 우회"를 실제로 해 본 결과 (2026-09-17 밤, user-timeline)

§3의 세 우회 중 **정적 링크(fat static) + 직접 참조**를 구현해 재봤다. 요지:

- 링커 제약: 공유 라이브러리(.so)를 만들 때는 다른 파일의 심볼을 `prefetcht1 sym(%rip)`처럼 상수 거리로 적을 수 없다(bfd·lld 모두 거부, `-z notext`로도 불가). 그래서 "한 파일" 조건을 만드는 유일한 방법은 라이브러리를 실행 파일 안에 정적으로 넣는 것이다. thrift·mongoc·bson·jaeger·opentracing·yaml-cpp·redis++·libstdc++를 정적으로 링크하면 NEEDED에는 libc·libssl·libsasl·libicu만 남는다.
- 그 위에서 pass는 "이 링크에서 해결되는 심볼 목록"(아카이브의 전역 심볼 13,456개)을 받아, 선언만 보이는 callee도 한 명령으로 프리페치한다. libc 함수만 `mov GOT; prefetcht1` 두 명령으로 남는다.
- 결과(기본 스케줄러, 3회): 정적 링크만으로 **1.039x**(MPKI 19.9 → 18.1; PLT/GOT 경유와 페이지 분산이 사라진 몫), 여기에 cold-path pass(함수 진입에서 자기 다음 라인 + 루프 밖 callee 첫 라인)를 얹으면 **1.045x**(MPKI 16.7). pass 자체의 몫은 twin 대비 1.8%이고, 추가 명령 1.8%가 그중 1.2%를 도로 가져간다.
- 같은 pass를 공유 라이브러리 빌드에 GOT 형태로 넣으면 1.007x에 그친다(명령 +2.2%). 즉 "명령 하나로 다른 파일의 코드를 가리키는" 능력(§4의 1번)이 하드웨어에 있으면 정적 링크 없이도 이 결과를 얻는다.

## 9. cold-path pass를 trace-guided plan으로 바꾼 뒤 (2026-09-18 새벽, 정적 링크 베이스 gs 대비)

정적 휴리스틱(함수 진입에서 자기 다음 라인 + callee 첫 라인)은 miss 안 나는 라인을 84% 겨냥하고 exe miss의 57%만 덮었다. 그래서 pass를 "plan 모드"로 바꿨다: LBR 붙은 L2I miss trace에서 miss 라인마다 branch 이력에서 60~4,000 cycle 앞에 있던 함수 진입 중 **실행 빈도가 가장 낮은 것**을 사이트로 잡고, 사이트 진입에 그 라인들만 `prefetcht1`(exe 라인은 pc-relative, libc 라인은 GOT 앵커+변위)로 심는다. burst는 16 B 배수로 패딩해 오프셋이 정확히 유지된다.

| 단계 | 결과 (gs 대비, 3회) | 배운 것 |
|---|---:|---|
| plan v1: 가장 이른 진입에 귀속 | 0.87x (miss −29%, 명령 +21%) | 사이트가 뜨거우면 요청당 수십 번 다시 prefetch |
| plan v4: 진입 빈도 최저 사이트 + 비용 필터 | 1.02~1.03x (miss −15%, 명령 +4%) | 사이트는 차가운 함수여야 한다 |
| epoch 게이팅(요청당 1회) | 1.014x (가드 −2.5%) | 가드 명령이 이득을 먹는다 |
| libc 타깃 제거 | 1.007x | miss의 43%가 libc; GOT 형태로라도 넣어야 한다 |
| **plan v10: 실측 실행 빈도로 가지치기** | **1.026x (miss −13%, 명령 +2.2%, twin 0.996x)** | 오버헤드는 잡혔고 남은 한계는 coverage |
| wake burst / orphan burst를 얹음 | 이득 없음 | 정적 사이트가 못 잡는 구간은 burst로도 안 잡힌다 |
| v4 5회 확인 (round 36) | **1.011x (twin 대비 1.019x, miss −13.5%)** | 데이터가 커지며 베이스가 느려져 상대 이득이 희석; 1~3%에서 포화 |
| **v10 5회 확인 (round 38)** | **1.022x 중앙값 / 1.032x 평균 (twin 대비 1.032x, miss −12.6%, 명령 +2.6%)** | 밤의 최선; 남은 miss는 정적 사이트가 앞에 없는 구간 |

남은 miss: libc 내부에서만 도는 branch 창(귀속 불가, 샘플의 10%), 그리고 wake 직후 소켓 읽기 경로(정적 사이트가 앞에 없음). 후자는 wake burst(LD_PRELOAD), 전자는 요청당 1회 "orphan burst"로 시험 중(round 29b/34/35). ISA 관점의 결론은 §4와 같다: 다른 파일의 코드를 한 명령으로 가리키는 주소 지정이 있으면 정적 링크 없이 같은 plan을 쓸 수 있고, "switch-in warm-up" 엔진이 있으면 wake 직후 경로까지 덮는다.

원래 공유 라이브러리 빌드 대비(round 39): 정적 링크 1.042x, 정적 링크 + plan v10 **1.070x**(코드 miss 19.7 → 15.9). 즉 "한 파일" 조건을 만드는 것이 절반, 그 위의 trace-guided prefetch가 나머지 절반이다.
