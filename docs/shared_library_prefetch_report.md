# 공유 라이브러리와 명령어 프리페치 — 왜 어렵고, ISA가 어떻게 도울 수 있나

2026-09-17. 컴파일러 배경이 없는 독자를 위한 요약. 근거 데이터는 README §5(DeathStarBench DSO 분해)와 §2-0(MariaDB PGO 빌드 실패 기록).

## 1. 우리가 넣는 명령이 요구하는 것

`prefetcht1 X`는 "주소 X의 64 B 라인을 미리 L2에 가져와라"라는 데이터 프리페치 명령이다. 코드 주소에 쓰면 명령어 프리페치가 된다.
x86-64에서 주소 X는 **"지금 실행 중인 명령 위치 + 고정된 거리"**로 적는다(rip 상대 주소). 즉 컴파일·링크 시점에
"내가 있는 곳에서 몇 바이트 떨어진 곳인지"가 **상수로 확정**되어야 한다.

이 조건은 하나의 실행 파일 안에서는 항상 만족된다. 코드가 어디에 로드되든 파일 안의 두 지점 사이 거리는 변하지 않기 때문이다.
Verilator·arcilator에서 잘 된 이유가 이것이다: 사이트와 대상이 같은 파일 안에 있다.

## 2. 공유 라이브러리에서 깨지는 세 가지

1. **거리를 모른다.** `libc.so`, `libstdc++.so`, `libthrift.so`는 실행 파일과 별개 파일이고, 프로그램이 뜰 때마다 OS가 **무작위 위치**(ASLR)에 올린다.
   실행 파일의 한 지점에서 libc의 어떤 함수까지 거리는 실행할 때마다 다르므로 상수로 적을 수 없다.
   우회하려면 "주소가 적힌 표(GOT)를 먼저 읽고, 그 값에 오프셋을 더해 프리페치"해야 하는데, 이건 **메모리 읽기 한 번 + 레지스터 하나**를 더 쓴다.
   메모리 읽기는 그 자체가 지연이 있고, 레지스터는 그 자리에서 비어 있어야 한다(호출 직전이면 비어 있는 레지스터가 있어 가능하다).
2. **우리 컴파일러가 만든 코드가 아니다.** 프리페치를 *넣는* 쪽도 문제다. libc·libstdc++ 안에서 miss가 나면 그 안에 명령을 넣어야 하는데,
   배포판이 이미 빌드해 준 바이너리라 우리 pass(컴파일 단계에서 명령을 끼워 넣는 도구)가 개입할 자리가 없다.
   DeathStarBench 서비스는 miss의 67–79%가 이런 라이브러리 안에 있었다(서비스 바이너리 자체는 21–33%).
3. **한 코드가 여러 파일에 들어간다.** 큰 프로젝트(MariaDB)는 같은 소스를 서버 실행 파일에도, 클라이언트 라이브러리에도, 도구에도 넣는다.
   서버에만 있는 함수를 가리키는 프리페치를 그 공용 소스에 넣으면, 서버 링크는 되지만 라이브러리·도구 링크는 "그런 주소 없음"으로 실패한다.
   우리가 6번 우회를 시도하고 포기한 이유다. 컴파일 단계가 아니라 **링크(파일을 조립하는) 단계**에서 넣어야 파일마다 다르게 넣을 수 있다.

한 줄 요약: **프리페치 대상 주소가 "파일 안의 상수"여야 하는데, 공유 라이브러리는 그 상수를 깨뜨리고, 라이브러리 코드 자체는 우리 손이 닿지 않는다.**

## 3. 지금 하드웨어로 가능한 우회

| 방법 | 비용 | 한계 |
|---|---|---|
| 링크 후 재작성: `call` 명령의 목적지를 우리가 덧붙인 작은 stub로 바꾸고, stub에서 프리페치 후 원래 함수로 점프 | 점프 1개 추가(1–2 사이클) | 사이트가 call/jmp 위치로 제한 |
| PLT 엔트리 재작성: 라이브러리 함수로 가는 관문(PLT)에 프리페치를 심어 GOT에서 읽은 실제 주소 기준으로 다음 라인들을 당김 | 추가 비용 0(원래 관문을 대체) | 라이브러리 함수 **진입** 라인만 |
| 전체를 정적 링크(fat static): 라이브러리를 실행 파일 안에 넣어 "한 파일" 조건을 회복 | 빌드 전면 재구성, 배포 형태 변경 | 8월 실험에서 miss가 분산돼 효과 ≈ 0 |
| GOT 우회 명령열(mov + prefetcht1) | 명령 2개, 레지스터 1개 | 사이트마다 비어 있는 레지스터 필요 |

## 4. ISA를 새로 설계하면 얼마나 간단해지나

핵심은 "주소를 상수로 못 적는다"는 제약을 하드웨어가 대신 풀어 주는 것이다. 세 가지 정도면 충분히 간단해진다.

1. **간접 프리페치 한 명령**: `prefetch [ [mem] + off ]` — "메모리에 적힌 주소를 읽어 그 위치를 프리페치"를 한 명령으로. 지금은 mov + prefetch 두 명령과 레지스터가 필요하다.
   GOT가 곧 그 메모리이므로, 라이브러리 함수 진입 프리페치가 사이트당 명령 하나로 끝난다.
2. **호출 대상 자동 프리페치 힌트**: `call` 명령에 "대상의 앞 N 라인을 미리 가져와라" 비트. 대상 주소는 하드웨어가 어차피 계산하므로 소프트웨어는 주소를 몰라도 된다.
   ASLR·공유 라이브러리 문제를 통째로 없앤다. 우리 실험의 callee-entry burst(4–8라인)가 이 힌트 하나로 표현된다.
3. **스트림 프리페치 명령**: "현재 위치부터 앞으로 D 바이트를 순차적으로 가져와라"를 한 번 발행하면 하드웨어가 이어서 수행.
   Verilator에서 70 B마다 프리페치를 심어 명령 수가 6% 늘었던 비용을 거의 0으로 만든다. 현재 `prefetchit0/1`은 이 역할을 못 한다(측정상 no-op).

이 셋은 새 주소 지정 모드 하나, `call`의 힌트 비트 하나, 프리페처 제어 명령 하나로, 디코더나 캐시 구조를 바꾸지 않는다.
반대로 지금 ISA로는 (a) 공유 라이브러리마다 링크 후 재작성, (b) GOT 우회, (c) 정적 링크 중 하나를 골라야 하고, 어느 쪽도 "명령 하나"가 아니다.

## 5. 지금 프로젝트에 대한 시사점

- 단일 파일에 코드가 있는 부류(flattened 시뮬레이터)에서는 현재 ISA로도 충분히 이득이 난다(Verilator 1.149x, arcilator 1.543x).
- 서비스 부류(DeathStarBench)는 miss가 라이브러리에 흩어져 있어 링크 후 재작성 + PLT 재작성이 현실적인 최선이고, 그 결과가 곧 "새 ISA 없이 갈 수 있는 한계"가 된다.
- 논문에서 ISA 제안을 한다면 위 2번(호출 대상 프리페치 힌트)이 가장 작고 효과 범위가 넓다.

## 6. 실측 (2026-09-17 밤, DeathStarBench user-timeline, 자세한 표는 `flat_codegen/dsb_build/postlink/RESULTS.md`)

§3의 우회 방법을 전부 구현해서 재빌드 없이 stock 바이너리와 .so에 적용했다.

- **call 사이트 stub, PLT 엔트리 재작성, 요청당 hot-set burst**: 모두 효과 0(프리페치를 NOP으로 바꾼 쌍둥이와 같음).
- **trace 기반 배치**(어느 call 사이트에서 몇 사이클 뒤 어느 라인이 miss 나는지 LBR로 찾아 그 사이트에 넣음, 다른 .so의 라인은 GOT를 기준으로 주소 계산): miss 11% 감소(MPKI 22.3→19.8), 그러나 stub 때문에 명령이 5.7% 늘어 실제 CPU 시간은 **1% 개선**에 그침.
- **전면 재빌드**(서비스와 thrift·mongoc·bson·jaeger를 clang-19 + 우리 IR pass로 다시 컴파일, callee-burst 또는 seq 모드): 효과 0(1.001x / 0.992x). 라이브러리 안에 프리페치를 넣을 수 있게 되어도 miss가 줄지 않는다.
- **trace 기반 배치를 재빌드로 inline 주입**(stub 없음, 공유 라이브러리도 GOT 기준으로 같이 주입): 비고정 1.012x, 메인 스레드 전용 코어 + 워커 풀 4코어 고정 시 1.003x(miss 5.7→5.5). 삽입 비용을 없애도 남는 이득은 1% 안팎이다.
- **대조군: 서비스를 코어 4개에 고정**: miss가 22.5→6.4로 1/3.5, CPU 시간 **33% 감소**. 즉 이 서비스의 명령어 miss는 코드가 커서가 아니라(hot 라인은 66 KB뿐) 86개 코어를 26개 컨테이너가 나눠 쓰며, 스레드가 요청 사이 쉬는 30 ms 동안 다른 컨테이너가 그 코어의 L2를 지우기 때문이다.

시사점: 공유 라이브러리 문제는 §3·§4의 방법으로 기술적으로는 풀 수 있지만(cross-DSO 주소도 GOT anchor로 해결됨), 데이터센터 서비스의 miss 원인이 "예측 가능한 스트림"이 아니면 프리페치 자체가 답이 아니다. §4-2의 호출 대상 힌트도 이 경우 lead가 부족해 같은 한계를 가진다. 반면 flattened 시뮬레이터처럼 한 파일 안의 순차 스트림은 현재 ISA로도 충분히 잡힌다.
