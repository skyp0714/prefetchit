# RPC 프리패치 실험 인수인계

다음 에이전트가 기존 결과를 재해석하거나 중복 실행하지 않고 후속 실험을 시작하기 위한 문서다. 사용자 목표는 **RPC 실행 흐름으로 앞으로 필요한 코드를 예측해 전체 요청 처리량과 지연을 개선하는 것**이며, 목표 이득은 약 10%다. 현재 유지할 정책은 `full`이고, 독립 확인에서 원본 대비 처리량 **+2.75%**다. 최신 RPC 추가 정책들은 이 위에 더해지는 이득을 입증하지 못했다.

상태 확인 시각은 **2026-10-02 22:03 America/Chicago**다. 진행 중인 실험 제어 프로세스, 소유 실험 컨테이너·네트워크·볼륨, 프리패치 커널 모듈은 없다. 이 인수인계 작업에서는 새 성능 실험을 시작하지 않았다.

## 사용자 의도와 운영 범위

- **항상 speedup을 먼저 보고한다.** 처리량, 평균/p99 지연, CPU/request를 함께 제시하고 원본 대비와 기존 정책 대비를 구분한다.
- 코드 미스가 줄었는데 성능으로 이어지지 않으면 원인을 조사한다. RPC 종류, 호출 흐름, 실제 trace, 결과가 준비되는 시점 등을 활용한다. 런타임에서 알 수 없는 미래 결과를 정답처럼 사용하지 않는다.
- 초기에 몰아서 발행하는 방식뿐 아니라 실행 경로를 따라 나눠 발행하고, 힌트 수·커버리지·코드 증가를 조절하는 방향을 이미 여러 번 시험했다.
- 사용자에게 설명할 때는 한국어로 간결하게 쓰고, 앱 서버와 MongoDB를 구분한다. `native` 같은 내부 이름을 설명 없이 쓰지 않는다.
- sudo와 구현·결과의 Git push는 기존 대화에서 승인됐다. **비밀번호를 문서·소스·로그·Git에 넣지 않는다.** 새 세션의 인증 상태를 확인한다. 과거 PTY 세션 번호는 재사용하지 않는다.
- 사용자는 당시 독점 사용 시간의 외부 계산 부하 종료를 명시적으로 허용했다. 해당 작업은 종료했고 감사는 로컬에 남겼다. 다음 세션에서는 현재 프로세스와 작업 범위를 새로 확인한다. 과거 PID로 신호를 보내거나 관련 없는 파일을 삭제하지 않는다.
- 과거의 “7시간”, “10시까지”는 당시 작업 일정이다. 새 세션에서 자동으로 새 마감이나 무기한 실행을 만들지 않는다. 현재 요청은 인수인계 정리다.

## 벤치마크와 측정 조건

대상은 DeathStarBench Media의 **compose-review 요청 전체 경로**다. MovieId를 포함한 앱 서버 9개, MongoDB 3개 및 부속 서비스가 함께 실행된다. 모든 Media API를 검증한 결과도, MongoDB만 단독 실행한 결과도 아니다.

흐름은 `리뷰 요청 → 여러 앱의 정보 처리와 DB 조회 → 다섯 결과 모으기 → 리뷰 저장과 사용자별·영화별 목록 갱신 → 응답`이다. RPC는 서버 사이의 작업 요청이다. 앱은 응답이나 다른 작업의 완료를 기다렸다가 다시 실행한다. 요청 추적 기능을 모든 요청에 켠 조건이어서 추적·로그 코드도 분석 범위에 들어간다.

| 항목 | 고정 조건 |
|---|---|
| CPU | Intel Xeon 6787P Granite Rapids, 86코어, SMT 없음 |
| 커널과 perf | Linux 6.8.0-142, perf 6.8.12 |
| CPU 배치 | 서버 32–39, 부하 생성 16–19, 제어·분석 84–85 |
| 운영점 | 2GHz, 동시 요청 4개, 지속 연결, CPU 사용률 약 85% |
| 요청 분포 | 기존 balanced workload와 데이터 검증 유지 |
| 성능 회차 | 매회 새 스택·데이터, 50초 예열 후 60초 측정 |
| 진단 | 성능 측정과 별도 실행. 서비스별 미스 표본은 보통 8초 |
| Docker 프로젝트 | `codex-b-fullset-media` |

최대 처리량을 이번에 새로 찾은 부하 스윕은 아니다. 과거 동시성 비교는 [고밀도 및 동시성 보고서](class_b_dense_and_concurrency_20260927.md)에 있다. 각 회차의 CPU 주파수·HWP 설정은 정확히 복원했다.

`full`은 이전 `pathwide_shared_anchor` 정책이다. **split75와 같은 이름으로 취급하지 않는다.** 앱·MongoDB·공유 라이브러리의 기존 최적화를 포함한다. 최신 캠페인은 앱 실행 파일에만 새 힌트를 추가했고 기존 MongoDB·공유 라이브러리 정책은 유지했다. “새 DSO 힌트 없음”과 “모든 DSO 최적화를 끔”은 다르다. 현재 채택 정책에 프리패치 커널 모듈은 없다.

## 확정된 성능 결과

개선율은 동일 블록의 로그 비율이며 구간은 개별 paired-log 95% 구간이다. 단계별 결과를 합치거나 서로 다른 단계의 효과를 곱하지 않는다. 아래 지연과 CPU 열은 감소가 개선이다.

| 단계와 비교 | 처리량 변화 | 평균 지연 변화 | p99 지연 변화 | CPU/request 변화 |
|---|---:|---:|---:|---:|
| 독립 6블록 `full / original` | **+2.75% [1.57, 3.95]** | −2.75% | −2.12% | −3.14% |
| 같은 단계 `reply_it0 / full` | −0.85% [−2.38, 0.70] | +0.88% | −0.07% | +0.13% |
| 같은 단계 `reply_it0 / reply_it0_nop` | −0.11% [−0.75, 0.53] | +0.11% | −0.44% | −0.09% |
| 별도 4블록 `stack / full` | **−0.41% [−1.80, 0.99]** | +0.41% | −0.16% | −0.11% |
| 같은 추가 단계 `stack / stack_nop` | −0.09% [−0.69, 0.53] | +0.08% | +0.31% | −0.04% |

두 추가 정책 모두 승격하지 않았다. 추가 이득을 확인하지 못했으며, 유의한 악화를 입증한 결과도 아니다. `stack` 단계에는 original 실행이 없다.

6블록 비교의 산술평균은 원본 1195.41 RPS, 기존 정책 1228.32 RPS다. 평균 지연은 3.2757 → 3.1855ms, p99는 5.7895 → 5.6667ms다. 별도 `stack` 단계의 기존 정책은 1222.27 RPS, 추가 정책은 1217.15 RPS다. 단계 간 절대값 차이를 정책 효과로 읽지 않는다.

이전 타이밍 확인에서 같은 full의 원본 대비 +4.19%, 응답 정책 탐색에서 full 대비 +1.49%가 나온 적이 있다. **최종 확인보다 좋은 탐색 수치를 골라 최신 성과로 보고하지 않는다.** 종전 약 2%와 이번 +2.75%의 차이를 새 정책의 추가 이득이라고 주장하지 않는다.

완료 기록은 주 E2E 90회, 외부 부하·전환 조건 보조 E2E 19회, 기능 검사 15회, 일반 미스 capture 107개, 호출 스택 진단 2개다. PMU 진단은 유효 4회와 기술 검증에서 제외한 1회가 있다. 최종 감사는 CPU 설정 복원 5,256개 기록, 요청 오류·매핑·표본 품질, 실험 자원 정리를 확인했다.

| 이름 | 변경 내용 | 결과 해석 |
|---|---|---|

| `stack` | 복원된 호출 스택으로 Compose의 RPC 문맥을 추가 활용 | 40개 T1, 5개 지점, 317바이트 추가. 독립 확인에서 추가 이득 없음 |

`reply_it0_nop`은 **새 응답 힌트만** 끄며 입력 RPC 힌트 52개는 유지한다. `stack_nop`은 새 40개만 끈다. NOP은 같은 코드 배치에서 새 prefetch 실행 효과를 구분하는 대조군이다.

`stack`은 full의 Compose 힌트 642개를 바이트 단위로 보존한다. 훈련에서 RPC가 호출 스택으로만 하나로 식별되고, 실제 handler 호출 뒤에 관측된 타깃을 골랐다. RPC별 최소 10표본·상위 8개이며 서로 다른 타깃 라인은 19개다. 스택을 걷는 작업은 훈련 때만 하고 실제 요청 중에는 하지 않는다.

더 이전의 실험을 다시 제안하기 전에 다음 기록도 확인한다. 조건과 정책이 다르므로 아래 보고서의 좋은 수치를 최신 결과와 합치지 않는다.

## 워크로드에서 확인한 현상

### 미스의 종류와 발생 위치

L1I와 L2 코드 미스는 필요한 명령어가 가까운 저장소에 없는 현상이다. ITLB 미스는 명령어 주소를 실제 메모리 위치로 바꾸는 정보를 못 찾는 현상이다. BTB는 분기 목적지를 기억하는 표다. 분기 예측 실패와 BTB 정보 부재는 같은 사건이 아니다.

- 앱, 통신·결과 처리, 추적·로그, 공통 라이브러리, MongoDB 내부 경로에 미스가 분산된다. 최근 앱 표본의 서로 다른 서비스·이미지·코드 라인은 4,072개이고 상위 100개가 전체의 약 14%였다. 전체 코드 크기나 성능 상한을 뜻하지 않는다.
- 앱 사용자 코드의 frontend 지표는 약 74%, backend는 약 8%다. Frontend는 다음 명령어를 준비하는 부분이다. **이 비율은 요청 지연의 비율이 아니며, 남은 74%를 전부 BTB 비용으로 볼 수 없다.**
- 원본 세 앱의 별도 진단에서 주소 변환 작업이 진행 중인 시간이 사용자 CPU 사이클의 약 9–12%였고 분기 예측 문제도 관측됐다. 서로 겹치는 지표이므로 독립 원인 비중으로 더하지 않는다.
- 충분히 예열한 뒤에도 발생하므로 초기 시동 문제에 한정되지 않는다. 최초 접근, 용량 부족·충돌, 코어 이동에 따른 미스를 정확히 나누지는 못했다. 문맥 전환이 코드 캐시를 통째로 비우는 것은 아니다.

### 시간과 분기와의 관계

- 최근 앱 표본은 CPU 배정 후 **10–20µs에 미스가 조밀**하다. 2GHz 기준 약 2만–4만 사이클이다. 전체 미스의 약 36%가 이 구간, 약 38%가 20–50µs 구간이다.
- MongoDB는 밀도 정점이 약 20–25µs지만 누적 미스 약 66%가 50µs 이후다. 앱의 초기 시간 창을 DB 전체에 그대로 적용하지 않는다.
- 시간 0은 스케줄러가 작업을 선택한 시점이다. 미스는 사용자 코드에서 수집했고 시간 분모는 커널 실행도 포함한 스케줄 구간이다. 첫 사용자 명령 시점이나 실제 prefetch 선행 시간을 직접 잰 값이 아니다.
- 최근 미스 표본 약 92–93%는 분기 도착점 뒤 64바이트 안이다. 일반 명령어도 분기 근처에 많이 분포한다. 분기 명령 자체의 미스와 도착 후 코드의 미스, BTB 문제를 구분한다.
- 정밀 표본 교차 검증에서는 원본 세 앱의 미스 명령 자체가 분기인 비중은 3–7%였고 분기 도착점 근처 비중은 94–97%였다. 다른 표본 모드·정책의 수치를 하나의 분포로 합치지 않는다.

근거는 [최근 시간축](class_b_rpc_predict_20261002.md)과 [분기 표본 교차 검증](class_b_dense_miss_causes_20260927.md)에 있다.

### CPU를 놓고 다시 실행하는 과정

앱의 한 실행 구간 중앙값은 서비스별 23–43µs, 비실행 구간 중앙값은 74–556µs였다. 이전 CPU를 확인할 수 있는 재개의 약 43–55%에서 다른 코어로 이동했다. 이 비율은 미스 중 코어 이동이 원인인 비율이 아니다.

RPC 응답을 기다리다가 네트워크 입력이 없으면 CPU를 놓을 수 있고, 다른 작업 완료 대기도 있다. 응답이 이미 준비됐으면 RPC 경계에서도 계속 실행한다. **RPC 경계와 CPU 전환은 일대일이 아니며, I/O 호출도 항상 CPU를 놓는 것은 아니다.** 현재 Media 기록은 모든 전환을 시스템 호출·RPC 단계와 연결해 네트워크 대기, 동기화 대기, 실행 순서 변경으로 나누지 못했다. 이전 SocialNetwork의 시스템 호출 문맥 진단을 Media 전체의 대기 원인 통계로 재사용하지 않는다.

### 선택한 타깃의 효과와 전체 효과

응답 정책의 입력·응답 고정 타깃 합집합에서는 미스가 **81.23 → 58.02/request, 28.57% 감소**했다. 하지만 해당 주소는 기존 전체 앱 표본의 5.30%였다. 전체 앱 PEBS 미스 감소는 1.09%였고 별도 perf-stat의 retired L2 miss/request는 1.14% 증가했다. 확실한 전체 미스 감소라고 주장할 수 없다.

최신 stack 정책의 Compose 단일 표본 비교는 다음과 같다.

| 항목 | 기존 full | stack | 변화 |
|---|---:|---:|---:|
| 전체 miss/request | 330.93 | 375.52 | +13.47% |
| 고정 타깃 시작 라인 | 15.45 | 8.90 | −42.41% |
| 고정 타깃 끝 라인 가정 | 34.59 | 15.52 | −55.13% |

전체 증가 44.59/request 중 원래 앱 코드 +28.61, 공유 라이브러리 +9.63, 기존 삽입 코드 +2.08, 새 삽입 코드 +4.08이었다. 새 코드 자체의 미스는 증가분의 약 9%다. **정책별 한 번의 Compose 표본이다. 전체 시스템 악화나 캐시 오염의 인과 증명이 아니다.** 이 관측과 독립 E2E 결과를 분리한다.

## 호출 스택 복원에서 수정한 문제

추가 진단의 첫 호출 스택은 앱 실행 파일에서 대부분 한 프레임만 남았다. perf 6.8의 libunwind 경로가 ELF 기준 주소를 `min(map.start - map.pgoff)`로 계산하는데, 삽입한 실행 구간은 파일 오프셋이 가상주소보다 커서 기준 주소가 잘못됐다.

오프라인 전용 ELF 사본의 파일 배치와 대응하는 perf MMAP 오프셋만 보정했다. **실행한 프로그램, 가상주소, 코드·CFI 바이트, SAMPLE 기록은 바꾸지 않았다.** 같은 14,411개 표본의 식별자와 leaf 주소, MMAP 오프셋 외 perf 바이트 동일성을 확인했다.

| 같은 표본의 지표 | 보정 전 | 보정 후 |
|---|---:|---:|
| 물리 프레임 2개 이상 복원 | 17.67% | 98.81% |
| 호출 스택으로 RPC 하나 식별 | 14.78% | 62.14% |

보정 후 전체의 39.00%는 짧은 분기 기록에서 놓쳤지만 스택에서 RPC를 복원했다. 이것을 새 stack 정책의 훈련에 사용했다. **분석 품질 개선이며 speedup이 아니다.** 앞선 일반 PEBS 주소 분석은 PT_LOAD별 매핑을 처리했으므로 이 추가 DWARF 문제 때문에 앞선 E2E와 모든 미스 분석이 무효가 된 것은 아니다.

관련 자료는 `ROOT/callchain/unwind_probe/`의 `normalization_comparison.json`, `normalization_manifest.json`, `summary.json`, `observations.json.gz`다. 첫 진단은 `ROOT/callchain/full/`에 따로 있다. raw perf, decoded text, 임시 ELF 사본과 symfs는 모두 추출 후 제거했다.

주의할 구현 세부 사항:

- 현재 호출 스택 도구는 Compose를 전제로 한 부분이 있다. 다른 앱으로 확장하려면 해당 경로·RPC 범위를 매개변수화해야 한다.
- perf 출력에서 첫 스택 프레임이 표본 주소인 형식이 있다. DSO 이름이 붙은 분기 기록 줄을 스택 프레임으로 오인하지 않는다. 현재 파서는 이 문제를 처리한다.
- 여러 호출 지점이 공유하는 삽입 코드를 마지막 호출 지점 하나에 귀속하면 안 된다. 현재 추가 진단은 복수 문맥을 보존한다.
- 살아 있는 호출 스택에는 비동기 작업의 부모 RPC가 없을 수 있다. 복원 실패를 소프트웨어 예측 불가능으로 해석하지 않는다.

## 다음 실험 후보와 실행 순서

아래는 **아직 검증하지 않은 후속 방향**이다. 최신 실패 결과를 숨기거나 기존 결과를 덮어쓰지 말고 별도 정책으로 검증한다.

1. **결과가 모두 모였는지를 이용한 발행.** Compose의 다섯 입력 중 완료 카운터가 5일 때만 결과 결합과 후속 저장 경로로 들어간다. RPC 이름만 보고 무거운 후속 코드를 먼저 읽는 대신, 이 조건이 확인된 뒤 해당 경로를 대상으로 삼는 후보가 있다. stack은 handler 첫 호출에서 발행했으므로 이 조건을 이용하지 않았다. 소스 근거는 `stack_followup/completion_state_source.json`과 그 파일이 가리키는 보존된 `ComposeReviewHandler.h`다. 발행을 늦추면 선행 시간이 짧아질 수 있으므로 기존 위치와 같은 타깃·NOP으로 비교한다.
2. **마지막 대기 뒤의 발행.** 기존 reply는 응답 헤더 뒤지만 본문을 읽다 다시 대기할 수 있다. 본문 처리가 끝나 다음 경로가 확정된 시점, 또는 결과 대기에서 돌아온 직후를 별도 후보로 삼는다. 실제 다음 호출까지의 실행 여유와 코어 이동을 확인한다.
3. **CPU 전환의 원인 연결.** 스케줄 전환과 실제 시스템 호출 진입·종료, RPC 단계, 작업 완료 대기를 같은 시계로 수집한다. 네트워크 대기·동기화 대기·선점을 나누고 각 재개 뒤의 미스를 비교한다. 현재는 이 부분이 characterization의 명확한 공백이다. 계측 오버헤드가 있으므로 성능 실행과 분리한다.
4. **보정된 호출 문맥을 다른 앱에 확대.** 타깃 밖 증가가 재현되는지도 독립 표본으로 확인한다. RPC당 같은 코드가 실제 필요한 빈도를 고려하고, 추가 힌트를 기존 발행 지점에 합칠 수 있는지 검토한다. 단순 밀도 증가나 “모든 잔여 미스는 lead-time 부족”이라는 가정으로 시작하지 않는다.

우선순위는 작은 정책 하나와 대조군을 고정해 검증하는 것이다. 새로 모은 진단을 훈련에 쓰면 그 뒤에 새로운 성능 검증을 수행한다. 훈련 자료와 검증 자료를 섞지 않는다.

## 재개할 때 지킬 측정과 해석 규칙

- **완료된 ROOT로 실행 드라이버를 다시 시작하지 않는다.** `rpc_predict_stack.py`는 `stack_followup`을 새로 만드는 단일 캠페인용이다. `rpc_predict_unwind_probe.py`는 이미 제거된 raw 파일과 고정 경로를 전제한다. `publish`도 새 목적지 전제다. 새 실험 루트와 명시적 프로토콜을 만들고 필요한 함수를 재사용한다.
- 원본과 full의 경로·해시·패치 계보는 `arms.json`과 기존 프로토콜에서 읽는다. 현재 full의 실제 파일은 `/storage/prefetchit/class_b_temporal_20261001/builds/pathwide_shared_anchor/` 아래에 있다. 긴 해시 경로를 추측하지 않는다.
- 새 후보, 같은 코드 배치의 새 힌트만 끈 NOP, full을 비교한다. 원본 대비를 주장할 때는 해당 확인 단계에 original도 포함한다. 단계 간 이득을 합치지 않는다.
- 순서·seed·반복 수·타깃·채택 기준을 측정 전에 고정한다. 최근 기준은 full 대비 처리량 95% 하한 양수, CPU 증가 0.5% 이내, p99 증가 2% 이내였다. NOP 비교는 별도 효과 분리다.
- PMU와 trace의 처리량을 clean E2E에 섞지 않는다. 기능 검사와 요청·데이터 검증을 통과한 뒤 성능을 잰다. 유효한 느린 회차를 지우거나 다시 실행하지 않는다.
- 표준 L2 표본 주기는 **1021**, 추가 DWARF 진단은 **257**이다. GNR의 retired L2 이벤트는 `event=0xc6,umask=0x3,config1=0x13`이며 사용자 코드만 수집했다. 새 CPU·perf 환경에서는 기존 설정을 무조건 적용하지 않는다.
- speculative L2 code-read와 retired L2 miss는 다른 모집단이다. 둘의 차이를 잘못 예측한 경로의 미스 수로 계산하지 않는다. MongoDB의 MPKI 약 26% 하락은 요청당 명령 수 약 37% 증가와 함께 나타났고 miss/request는 줄지 않았다.
- 시간별 미스는 구간 길이와 CPU 노출 시간으로 정규화한다. 긴 시간 구간의 누적 미스와 순간 발생 밀도를 구분한다. 표본 요청수는 perf 시작·종료 구간을 포함한 근사 정규화다.
- 분기 기록의 cycle 합을 정확한 prefetch-to-fetch 시간으로 해석하지 않는다. 기록에 힌트 경로가 있다고 하드웨어 수용·완료를 증명하지 못하고, 최근 기록에 없다고 미발행을 증명하지도 못한다.
- 명령이 64바이트 경계에 걸치면 어느 라인이 미스했는지 확정할 수 없다. 시작·끝 라인 두 가정의 민감도를 함께 남긴다.
- raw 주소와 perf 매핑에는 실행 파일 SHA와 구간별 주소 매핑을 사용한다. 해시가 같다고 빌더 메타데이터의 경로까지 같다고 가정하지 않는다.
- PMU 진단 `full_core`는 top-down 합계 오차 2.778%로 기존 2% 기준에서 제외됐다. 같은 프로토콜의 `full_core_retry1`을 사용했고 E2E는 반복하지 않았다. 최초 split 미스 표본과 중단된 탐색은 외부 부하와 겹쳤다. 과거 “타깃 미스 41% 감소”를 동일 조건의 결과로 재인용하지 않는다.

## 정리와 다음 세션의 상태 확인

탈락한 실행 파일·object·임시 trace는 이미 제거했다. 파일이 없다는 이유로 원본 데이터가 삭제됐다고 판단하거나 모든 빌드를 다시 만들지 않는다. 필요한 후보만 보존된 계획과 소스로 재구성한다.

[AGENTS.md](../AGENTS.md)에 따라 매 빌드·실행 전 공간을 확인한다. 기존 실행기는 `/` 7GiB, storage 30GiB 이상의 여유를 요구한다. 인수인계 시점의 여유는 각각 약 14.4GiB, 850.2GiB였으며 새 실행 전에 다시 확인한다.

각 탈락·대체 실험은 compact 수치·설정·명령·소스·패치·해시·제외 이유를 먼저 보존한 뒤 불필요한 bulk를 바로 제거한다. 경로·제거 바이트·회수 공간을 기록한다. 원본 benchmark 소스·입력·공유 의존성·관련 없는 작업·활성 실험은 삭제하지 않고, symlink를 따라가서 지우지 않는다.

NAS는 `/fast-lab-share/hnpark2` 아래만 사용한다. 한 번에 rsync 하나, 기본 `--bwlimit=20480`, 새 목적지와 재개 가능한 partial을 사용한다. 공유 NAS에서 병렬 복사·무제한 checksum scan·`--delete`를 쓰지 않는다. 순차 속도 제한 SHA-256 검증 후 로컬 파일을 지운다. 측정할 실행 파일·입력은 같은 방법으로 로컬에 staging하며 NAS symlink를 통해 benchmark하지 않는다.

새 세션의 첫 확인은 Git 변경 사항, 현재 프로세스, 소유 Docker 자원, CPU 설정, 공간, 원본·full 파일 존재 여부다. 과거 세션 번호나 PID, 전날의 외부 부하 상태를 현재 사실로 취급하지 않는다. 보고는 **실제 speedup → 미스 변화 → 확인된 원인과 남은 불확실성 → 다음 수정** 순서로 한다.
