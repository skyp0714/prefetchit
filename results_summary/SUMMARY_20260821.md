# PrefetchIT 결과 요약 (2026-08-21, 하이레벨)

측정 원칙: 고정 클럭(코어+uncore 핀), 레이아웃 동일 NOP-쌍 대조군, 인터리브 ≥3회.
**프리패치 순수 효과만** (PGO/레이아웃 이득 제외).

## 한 줄 결론

프리패치가 이기는 조건 = **미스 많음 + 목적지를 미리 앎 + 시간 여유 + 가져다 놓은 자리가 안 뺏김**.
성공/실패 전부 이 네 조건으로 설명됨 (fig2).

## 성공 (fig1)

| 워크로드 | 이득 | 되는 이유 |
|---|---|---|
| Django (웹) | **+49%** | 핸들러 포인터를 읽는 순간 목적지 확정 → 긴 리드타임 |
| Verilator (EDA) | **+7.8%** | 100MB급 코드, 고정 실행 순서 (static plan이 PGO보다 나음, 주입 20배 적게) |

## 실패와 원인 (fig2)

- **OLTP (PG +0.3% / MariaDB 0)**: 미스는 많지만 데이터 트래픽이 L2를 계속 덮어씀 → 미리 가져다 놔도 사용 전 축출. **5번째 축: L2 데이터 압력**.
- **DSB 마이크로서비스 (0)**: 미스가 3.6천 지점에 분산 + 분기 직전에야 목적지 앎(리드타임 ~10 명령). 타입특화/딥 lookahead/라이브러리 내부 주입(GOT, 동적링킹 유지)까지 전부 시도 → cold 레짐 불변 (fig3). warm의 hard-core 미스만 −4.9% (E2E ≤0.5%).
- **실제 JVM 앱 40+ (0)**: 코드가 2MB L2에 다 들어감 → 미스는 L1I에서 발생, t1(L2-filler)은 무력. L1I를 채우는 prefetchit0는 이 CPU에서 no-op (측정 확인).
- **컴파일러/HPC/memcached 등 35+**: 미스 자체가 없음.

## 이번 주 방법론 발견 (wave-8)

이전 "라이브러리 내부 주입 → 중립" 실험(wave-6)은 **빌드 실패가 조용히 삼켜져 stock lib으로 측정된 null-arm**이었음.
(.so는 외부심볼 PC32 불가 → GOT 모드 필수; bash `A && B`의 A 실패는 set -e를 발동 안 시킴.)
수정 후 **최초의 유효한 in-lib 주입**으로 재측정 → 그래도 중립 → DSB 경계 결론은 유지되되 증거가 진짜가 됨.
교훈: **주입 검증(objdump 카운트) 없는 빌드 성공을 믿지 마라.**

## Emissary(ISCA'23)와의 정합

같은 앱을 쓰지만 하드웨어가 다름: Emissary는 gem5로 L1I 32KB / **L2 1MB** / L3 2MB victim을 시뮬 —
tomcat(코드 2.57MB)이 L2에서 넘쳐 L2I MPKI ~14. 우리 실측 tomcat도 L2I 10~13으로 **수치는 일치**.
차이는 미스 비용: 우리 GNR은 L2 2MB/코어 + L3 336MB라 L2I 미스가 수십 사이클 L3 히트로 끝남.
→ 다음 실험: **pqos로 LLC way 축소**해 Emissary류 구성 에뮬레이션.
