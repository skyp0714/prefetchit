# JVM A-2/A-3 qualification and intervention protocol

Scope: new Artemis, Keycloak, Flink/Nexmark, OpenSearch, Pinot; refreshed Renaissance (finagle-chirper/http, dotty, future-genetic, db-shootout), Tomcat/Spring; previous Solr/Cassandra/Trino included in status matrix. Existing measurements are identified as such.

G2: surviving direct Java calls in the optimized C2 graph, sorted by root call-site BCI; entry injection reloads current Method::from_compiled_entry. F: future virtual/interface receiver from unchanged entry parameter or single final reference field; actual receiver vtable/itable lookup, no history predictor. This initial F does not cover arbitrary next queued objects. Selection uses no external trace/profile; ordinary C2 optimization still uses normal runtime type profiles. F2 also rejects any original call site with an inlined root callee, even if a fallback call survives. BCI is a lead-time heuristic, not measured cycles. Only G1/Parallel/Serial GC, normal non-OSR C2 roots, resolved linked metadata; nullable receivers skipped; no speculative execution or early call. Method metadata references use standard nmethod relocations. Need emitted-code, result, GC/recompile tests before workload use.

Existing v2/v4 flags remain disabled. Compare same experimental JVM binary with G/F flags off/on; stock vendor JVM screening is not an A/B baseline for that binary. Primary timing without perf attached; separate PMU and PEBS runs. Baseline/G/F/GF plus exact-byte-length hint-NOP control. Start one fresh JVM per mode for screening. Predeclare best real-hint mode with >=1% primary-metric improvement per workload, including the separate Pinot BCI pilot, for five new randomized blocks of baseline/selected mode/its own matched NOP. Do not reuse screening values in paired log-ratio t(4)95% intervals. Report uncertainty; one-JVM gains are not confirmed. Flink confirmation uses all-arm >=180s plus three10s compiler<=1% warm windows (max300s), because initial65s screens retained1.6–1.7% compiler CPU in G/F. Include lookup/instruction/code-size overhead.

4 target cores 32-35, 2 GHz/C6 off controlled/restored by existing wrapper; client cores16-19. Run serially, no builds/transfers during measurement. Preserve normal GC/inlining/code-cache limits. >=60 s/>=5 complete warmup operations and >=30 s/>=3 complete measured operations for JVM suites; benchmark-specific result validation explicitly distinguished from harness success. Finagle-chirper and db-shootout warn that semantic validators are absent.

Keep <=compact records locally; remove generated scratch each completed attempt. Shared source, original inputs/distributions protected. New JVM build uses existing experimental OpenJDK tree; preserve before files/old binary and final relative patch. Failed in-progress build outputs remain active until fixed, abandoned variant bulk then removed. NAS transfers only serialized rsync20MiB/s plus sequential limited SHA256, not during accepted measurements.

Confirmation refinements declared before any confirmation runs: DaCapo uses the existing callback property window.warmup.seconds=180 in every arm (minimum five complete warmup operations remains); suites optionally snapshot threads immediately around primary CPU timing for diagnostics. Existing first-screen timing remains unchanged. Flink adds a separate post-primary30s L2I/ITLB PMU window with full-scheduling/source-progress checks; it is never used as the primary CPU gain window.

Renaissance confirmation also uses the180s property through a separately built configurable policy jar; build/source hashes are in confirmation_policy/build.json. All75 planned confirmations completed without replacing valid runs. The post-completion background audit retains every run; its Pinot block3 sensitivity is explicitly post hoc and never substituted for the primary five-block statistics.
